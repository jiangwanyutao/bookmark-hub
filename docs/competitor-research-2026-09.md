# 书签扩展竞品调研

调研时间：2026-09-16。覆盖 Edge 外接程序商店、Chrome 网上应用店、跨浏览器同步方案。
Edge 数据来自商店官方接口 `getproductdetailsbycrxid`（实测值）；Chrome 数据取商店页显示值（Google 本身分桶取整）。

---

## 一、结论先说

**守住两个零竞品能力：失效的四态分类、恢复点撤销。不做同步、不做云收藏、不做磁贴新标签页。**

三块不碰的理由很硬：同步有 floccus（Chrome 10 万 / Edge 2.9 万）开源免费在前；云收藏有 Raindrop（Chrome 50 万 / Edge 11.4 万）规模在前；磁贴新标签页在中文市场有 iTab（Edge 174 万装机）这种量级，而书签类磁贴也有 Speed Dial [FVD]（Chrome 50 万装机、11.78 万条评分）十年沉淀。

两个要立刻处理的问题：**撞名**（见第五节）和**商店文案没讲差异点**（见第六节）。

---

## 二、我们的差异点，逐条核对

| 能力 | 竞品现状 | 我们 | 判断 |
|---|---|---|---|
| 失效检测区分「需登录」 | 全网只有 LazyCat 在内部避让（401/403 直接判为「有效」只附一句 reason），**不给用户独立分类** | `classify.ts:116` 401/403 → `need_login`，归 `unknown` 不归 `broken`；另有登录跳转识别 `isLoginUrl` | **零竞品** |
| 失效检测区分「可能需要 VPN」 | **全网没有一家提** | `classify.ts:105` 受限网络或已标记域名 → `maybe_vpn`；用户可在设置里维护 VPN 域名表 | **零竞品** |
| 失效检测区分「被限流」 | 未查到有人做 | `classify.ts:117` 429 → `rate_limited`；`request.ts:168` 按 Retry-After 退避重试一次 | **零竞品** |
| 重定向识别并一键更新 | ClearMark（Chrome）、Bookmarks Organizer（Firefox）、收藏夹 chengu（Edge 141 装）有；LazyCat 追踪跳转但不作为可清理类别 | 有，独立页面 | 有重叠，不是壁垒 |
| 操作记录 + 恢复点撤销 | **未查到任何竞品有**。Bookmarks clean up（Chrome 20 万，赛道天花板）官方明写「删除无法恢复，请先备份」；LazyCat 源码里搜不到任何 undo/restore 实现，商店描述同样建议先备份。仅 FindMark（Edge 135 装）有 90 天回收站 | 每批操作可单独撤销 + 恢复点整体回滚 | **近乎零竞品** |
| 重复书签分级清理 | Bookmark Dupes（Chrome 2 万、4.9 分，有正则专家模式）口碑很好但只匹配 URL 完全相同；Edge 上纯去重三家全是精确匹配 | 完全相同 / 规范化后相同 / 疑似相同三级 | 有优势，不独有 |
| AI 整理目录 | 概念上有一堆，**无人跑出来**：Neat AI 466 装、Bookmark Genie 720 装（1.8 分）、MarkAI 173 装、Just Mark 1265 装（3.0 分） | 有，用户自带 OpenAI 兼容 key | 赛道空着 |
| 书签导航磁贴页 | Speed Dial [FVD] 50 万装 / 11.78 万评分；中文侧 iTab 174 万装 | 有 | **不该当主打** |

### 最现实的对手：LazyCat Bookmark Cleaner（懒猫书签清理）

Edge 5,333 装机 / 4.9 分，开源 MIT（[Alanrk/LazyCat-Bookmark-Cleaner](https://github.com/Alanrk/LazyCat-Bookmark-Cleaner)，1850 star），最后推送 2026-01-12，商店版本停在 2025-03-04。

它的检测实现：`fetch(no-cors)` + `AbortController` 超时，配合 `webRequest.onBeforeRedirect` / `onHeadersReceived` 抓真实状态码。判定上 401/403/405/406/407/408/429 全判为「有效」，503/504/502 有效，500/501 失效。

**它唯一一条差评正中我们的靶心**（2025-07-03）：「清理失效书签这块不是很准确，很多扫出来失效的，实际是正常可用的状态」。

这说明：**检测准确度是这个品类的真痛点，而不是功能多少。**

### 行业级硬伤：Cloudflare / WAF 误报

Cloudflare 把链接检查器当未知 bot 返回 403，页面其实活着。这是全行业问题，Cloudflare 社区和 linkchecker 项目都有长期 issue，WordPress Broken Link Checker 的开发者说「无法通过任何 Cloudflare 规则绕过，除非被白名单」。

我们把 403 归到 `need_login` 而不是 `broken`，方向是对的，但**归因文案可能需要调整**——403 更常见的原因是 WAF 拦截而不是需要登录。

### AI 整理这条赛道：全是小玩家，且有翻车样本

Bookmark Genie（720 装）拿了 **1.8 分**，但**翻车原因不是 AI 效果差，而是接入环节全线崩**：Google 登录点了不跳转、Brave 上 OAuth 报 "Access blocked"、Groq key 配不上。原始差评：「it dont work dont pay developers the api wont allow grok key they ran off with developer fee」。

**对我们的直接教训**（我们走的是同一条「用户自带 key」的路）：

1. key 配置环节的**连通性自检和报错可读性**，比模型选型重要得多
2. 它自带 key 还要 Google 登录，这个多余门槛本身就是差评来源——我们纯本地无账号，天然占优

### 收费模式

- **一次性买断：未查到任何一例**，这个品类里买断制事实上不存在
- 订阅只出现在有服务器的产品上：Raindrop Pro $3/月、Toby $6/月
- 纯本地工具类几乎全部免费

**结论：纯本地 + 用户自带 key，收费空间极窄，不建议规划订阅。**

## 四、跨浏览器同步：建议不做，但记下最小可行方案

### 为什么这条路难

浏览器书签 ID 是本地生成的，不跨设备、重装即变。要真正合并就必须维护「本地 ID ↔ 远端 ID」映射表，**这张表一失效就是全量重复——这是 floccus 所有重复 bug 的共同根源**。

floccus 的用户抱怨按频率排：

1. **制造重复书签**（压倒性第一，多个长期未解决 issue：#203、#382、#544、#744）。典型模式是一旦同步出错就不停造重复
2. **丢书签且备份救不回**（#1566：从 Google Drive 恢复历史版本，恢复出来是 450 字节空文件，原本 450KB）
3. **和浏览器原生同步打架**——官方 FAQ 自己要求用户先关掉浏览器自带同步，否则「会导致重复和数据损坏」
4. 书签多了卡顿、配置门槛高

xBrowserSync 加密做得漂亮（AES-GCM + PBKDF2 25 万轮）但**已经死了**：仓库 2021/2022 年起无提交，149 个 issue 无人回复，Chrome 已因「不符合扩展最佳实践」禁用它。

MV3 还有个坑：service worker 空闲 30 秒被杀，已有开发者反馈 MV2→MV3 后用 alarms 做的定时同步不再工作。

### 真实需求场景（不是推断，是用户自述）

- 工作用一个浏览器、个人用另一个，刻意隔离但书签想共享（被点名最多）
- 不信任大厂、要自己掌握数据
- 正在迁移浏览器的过渡期

反过来，**纯粹换浏览器的一次性迁移，导出导入 HTML 就够了**，这两个人群规模差很多。

### 如果将来要做，最小可行做法

**不做 sync 引擎，做「带加密的云端导入导出」：**

WebDAV 或 GitHub Gist 二选一 → 单文件全量 JSON → 可选 AES-GCM 密码加密 → 手动触发。

单文件全量 = 不需要 ID 映射、不需要三方合并、不需要增量，直接绕开全部难点。冲突用最笨的办法：远端比本地新就弹框让用户选方向，**绝不自动 merge**。

四条省不掉的成本：

1. 覆盖前必须存完整快照 + 一键回滚（我们已有恢复点机制，这条基本现成）
2. 必须加变化比例阈值确认，别让用户一键删光
3. 必须在 UI 里明说「请先关掉浏览器自带同步」——这个问题从扩展内部无解
4. 隐私文案要改：「不收集数据」仍成立，但要补「同步会把书签发到你自己配置的服务器，我们不接触、不存储、不中转」，Edge 商店隐私声明也要跟着改
5. WebDAV 的 CORS 和认证是踩坑最多的地方，要能区分 CORS / 401 / 404 / 证书问题给出可诊断的报错
6. 长期支持成本高：这类功能的 issue 密度远高于纯本地功能，维护工时花在别人的服务器和别人的浏览器上

## 五、撞名问题（需要决策）

**`BookmarkHub - sync bookmarks`（dudor）**：

- Chrome 商店 10,000 用户 / 4.1 分（89 条），**2026-05-17 仍在更新**
- Edge 商店 4,982 装机 / 4.4 分（36 条）
- GitHub 2.6k star，Chrome / Firefox / Edge 三家全上架
- 宣传语：「去中心化、跨浏览器、端到端加密、无需注册、不收集数据」
- 还有个 fork：BookmarkHub Auto-Sync，也在 Chrome 商店

另有 `Bookmark Hub`（Kaosc，与我们完全同名）Chrome 23 用户、一年未更新，可忽略。

**实测搜索排名**：在 Edge 商店搜 `bookmark hub` 和 `BookmarkHub`（en-US），**前 20 名里都没有我们**；对方稳居第 2（第 1 是 Bookmark Sidebar 靠 14 万装机吃通用词）。Edge 搜索明显按装机量 + 评价数排，我们 0 装机 0 评价进不了首屏。

**三个后果**：

1. 搜索被盖死，用户搜「bookmark hub」找到的是它
2. 一旦我们做同步，就是正面打对方主场
3. 反向信号：它 4.1 分偏低，用户抱怨集中在「要自动同步」「Gist 配置看不懂」「要覆盖前警告和恢复机制」——这条路体验普遍不好，是红海

**建议**：改名，或至少加一个讲清差异的副标题。Edge 条目现在还能改，Chrome 尚未上架，现在是改名成本最低的时候。

## 六、可以立刻做的三件事

1. **改商店描述的第一句**。现在是「收藏了几百上千个书签之后……」，讲的是问题，没讲差异。建议改成讲差异点的那句：**「不会把需要登录的站当成死链删掉，删错了还能撤回」**。中文条目还没提交，现在改成本为零。
2. **决定要不要改名**。理由见第五节。
3. **复查 403 的归因文案**。我们把 403 归到 `need_login` 方向正确，但 403 更常见的原因是 Cloudflare / WAF 拦截而非需要登录，文案上可能要更准确。
